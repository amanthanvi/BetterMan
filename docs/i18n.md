# UI localization

BetterMan 2 B9 (#401) translates the interface, never the manual. This file is
the language contract that B3 (#395, translated manual pages) builds on.

## The contract

- **One parameter.** The language is the URL's `?lang=`, beside `?distro=`.
  Values: `en`, `de`, `fr`, `es`, `pt-BR`, `ja`, `ru` (matched without regard to
  case). A bare URL is English. On a man page the URL allowlist
  (`lib/manQuery.ts`, built from `LANGS`) drops `?lang=en`, so English is always
  the bare URL there, and redirects another spelling of a code (`?lang=DE`,
  `?lang=pt-br`) to the canonical one (`?lang=de`, `?lang=pt-BR`); App Router pages accept `?lang=en` as an explicit English
  that a remembered language does not override. An unknown value renders
  English, as if the parameter were absent, and a language that is not public
  yet renders English at its URL.
- **URL only.** Man pages are edge-cached HTML keyed by URL and dataset
  release. The renderer never reads a cookie or `Accept-Language`, so a
  localized page is its own cacheable page, and English stays the bare URL.
- **Public means reviewed.** Every catalog carries
  `status: 'needs-review' | 'reviewed'` in `nextjs/lib/i18n/catalog/<lang>/meta.ts`.
  A language renders publicly only when it is `reviewed`. All six are
  `reviewed` (2026-10-30): two model panels (GPT-6.1 Sol and Grok 4.7) read
  each catalog, every correction was applied, and an independent review checked
  that each one landed. B3's translated-manual notes (#395) were added later
  and reviewed by the same two panels on 2026-10-31, with every correction
  applied. Each `meta.ts` records the reviewers and the date. A new
  language, or a fix that changes a meaning, goes back to `needs-review` until
  it is read again; the gate still holds it back.
- **Previews.** `BM_I18N_PREVIEW` (a comma-separated list of codes, or `all`)
  makes a deployment show a language that is `needs-review`, for reviewers.
  Production does not set it, and nothing needs it while all six are reviewed.
  The unit tests hold a catalog back (`holdBack` in `lib/i18n/testing.ts`) to
  cover the gate.
- **Remembered like the distro, by a cookie.** The switch is two plain links
  (no script, no storage): `/-/lang/<code>` answers a private `307` that sets
  the `bm-lang` cookie (`Secure` over HTTPS) and returns to the page, which it
  reads from the same-origin Referer (a `?to=` also works). Neither kind of page
  puts the page in the link: a man page's HTML is cached per URL, so a `?to=` on
  each of six links would grow every man page, and the shared App Router layout
  cannot know the page after a client navigation. Without a Referer the reader
  lands on home, in the language. The return carries that language in its URL.
  `/-/fix/<code>` does the same for the translation-fix issue. `/-/` cannot
  start a command name, so neither collides with a short URL. Only the
  proxy reads the cookie: a bare URL (a man page, or any App Router page)
  from a reader who remembers a language other than English answers a private
  `307` (`Cache-Control: private, no-store`) to the explicit `?lang=` URL, as
  the distro cookie does (#449). The URL wins; an explicit `?lang=` never
  changes the remembered choice, and English is remembered like any language.
  The plain-text export is untranslated and never redirects.
- **Trusted header.** The App Router layout and `not-found` learn the language
  from the `x-bm-lang` request header the proxy sets from the URL. The proxy
  does not run for prefetches, so a client could send that header there; the
  renderer therefore honors it only beside the per-build secret
  (`x-bm-release-token`, as for the man pages' release), which the proxy sets
  and a client cannot know (`lib/i18n/request.ts`).
- **Links keep it.** Every in-app link carries the current URL's explicit
  `?lang=` the way it carries `?distro=` (`withDistro(loc, distro, lang)`,
  `manPageHref(…, lang)`). The shared layout cannot see a client navigation, so
  once a second language is public the App Router shell reloads when the URL
  names another language than the one it rendered.

## Section names

Sections 4 and 7 are "Special Files" and "Miscellany" in the running head,
the pills and the section pages. On FreeBSD and macOS the BSD manuals call them
"Kernel Interfaces" and "Miscellaneous Information", so those two read that way
when the page is from either system (`sectionLabel(section, t, distro)` in
`components/man/RunningHead.tsx`); both names are catalog messages.

## One source for the language list

`lib/i18n/locales.ts` is the single source of the language list, its validation
and the `?lang=` helpers; do not copy the list. B3's `lib/lang.ts` (#472) and the
man-URL query allowlist's `MAN_LANGUAGES` (#469) are meant to import from it
(`LANGS`, `LANG_PARAM`, `normalizeLang`, `translatedLang`, `LANG_LABEL`, and
`setLang` for its set-or-clear `withLang`; this module's `withLang` instead
*carries* the page's explicit choice, `?lang=en` included). Whichever of those
PRs merges last reconciles. `MAN_LANGUAGES` in `lib/manQuery.ts` already derives from `LANGS` (every language but English). Concept pages (B8, `/concept/<slug>`) stay English: their query allowlist is `distro` alone, so `?lang` redirects to the bare URL, and their shell is passed `englishI18n()` (only English public, so no language links), links into `/concept/` carry no `?lang=`, and the cookie redirect skips them, so nothing loops. Their chrome strings are still `t()` messages with translations, ready for when explainers are translated. Gate with `resolvePublicLang` where an unreviewed
language must not count.

## What a content-side agent reads

| Need | Where |
|---|---|
| The language list and validation | `lib/i18n/locales.ts`: `LANGS`, `normalizeLang`, `resolveLang(value, available)` (safe for the browser) |
| The review gate | `lib/i18n/gate.ts`: `publicLangs()`, `resolvePublicLang(value)`, `CATALOG_META` (server code only) |
| A page's language (App Router) | `explicitLang(sp)` / `resolveRequestLang(sp)` in `lib/requestContext.ts` |
| A man page's language | `manI18n(query.lang, currentHref)` in `lib/i18n/page.ts` |
| Strings, server side | `getI18n(lang)` in `lib/i18n/server.ts` |
| Links in a language | `withLang`, `withDistro(…, lang)`, `setLang`; the switch's own links are `langSwitchHref` / `fixLinkHref` in `lib/i18n/switch.ts` |
| `hreflang` groundwork | `hreflangAlternates(url, langs)` in `lib/i18n/seo.ts` |

The proxy validates `?lang=` with `resolvePublicLang`; a parameter allowlist
(#469) should call that function (or `normalizeLang` where the gate does not
apply) rather than carry its own list.

## SEO until translated manuals exist

A localized-UI page is the English manual under translated chrome. Until B3
ships translated manual content:

- every page rendered in another language is `noindex, follow` and names the
  **English URL** as its canonical (`lib/i18n/seo.ts`, the man page head);
- no `hreflang` alternates are emitted (they would claim translated manuals);
- sitemaps list English URLs only;
- Open Graph images, JSON-LD and the plain-text export stay English.

When B3 adds a translated manual, that page may drop `noindex`, canonicalize to
itself and emit `hreflangAlternates(…)`. UI-only pages keep the policy above.

## The catalog

**A message is its English text.** Code writes `t('Command palette')`, so an
English page, its bundles and its HTML carry no catalog at all: `t` returns the
text, filling `{name}` values and plurals. A translation is a map from that
English text to the language's. Two messages with the same English but different
translations are told apart by a context in front, `context` + U+0004
(`man.prefsLabel\u0004Reading preferences`); `t` drops it for English.

`nextjs/lib/i18n/catalog/<lang>/` holds four files per language. The English
files are lists of messages, used for types and tests only (no bundle imports
them): a translation is a `Record<Message, string>`, so a missing or extra
message fails `tsc`, and `catalog.test.ts` checks placeholders and plural forms.

| File | Shown by | Delivered |
|---|---|---|
| `common.ts` | the App Router client and the man page script (palette, preferences, shortcuts, contents, result kinds) | with the page (client) or built into the language's script (man) |
| `client.ts` | the App Router client and components the server shares with it (`common` plus the shell, home, search results, licenses, errors) | from the server in the page's props, plurals already expanded |
| `man.ts` | the man page script (`common` plus the composer, find, tables, previews) | embedded in that language's script bundle, `man.<lang>.<hash>.js` |
| `server.ts` | server-rendered pages only (metadata, section and package pages, explain, 404s, the man page's addenda) | never sent to the browser |
| `meta.ts` | review status, translator, reviewers | read by the gate |

The man page script is built once per language (`scripts/build-man-client.mjs`,
`scripts/man-i18n.mjs`). The English bundle erases the `t('…')` wrappers back to
the text they stand for and carries no dictionary, so it costs what the script
always did; each other language embeds its own strings, and a page loads only
its own script. The browser never downloads a locale it is not showing, and
English downloads none. 426 entries per language (416 distinct messages): 108
common, 79 client-only, 37 script-only and 202 server-only.

Messages use `{name}` for values and `{count, plural, one {# page} other {# pages}}`
for plurals, by the language's own rules (Russian needs `one`, `few`, `many`
and `other`). Placeholders that stand for elements (`{link}`, `{key}`) are
filled with `tRich`, so a translator moves them where the language wants them.

Not translated, by design: upstream manual text, the explain engine's facts
and diagnostics, generated summaries, task phrases and example queries (the
generated layer is English), command names, flags and code, key names, share
images, the plain-text export, the OpenSearch description and the last-resort
`global-error` page (which renders when the root layout itself has failed).

### Terminology

Follow the man-page community of each language: section names are those of
`man-db`/the language's man-pages project (`Benutzerbefehle`, `Appels système`,
`Llamadas al sistema`, `Chamadas de sistema`, `システムコール`, `Системные вызовы`);
a flag is an `Option`/`option`/`opción`/`opção`/`オプション`/`параметр`; the
404 uses the C library's `ENOENT` message for the language ("Datei oder
Verzeichnis nicht gefunden", "Aucun fichier ou dossier de ce type"), and a
missing manual says what `man` says ("Kein Handbucheintrag für …", "Aucune
entrée de manuel pour …"). Key names follow the local keycap: a German keyboard
prints Strg, so German prose says Strg; the keycaps the shortcuts dialog draws
are the key legends and stay as the keys are marked. Keep the English word
`Digest` in the error label so reports quote it. In gendered languages the
"new" badge agrees with "option" (fr nouvelle, es nueva, pt-BR nova).

The section names follow the dataset's own labels (`convex/lib.ts`, from
man-db): "Special Files" for section 4 and "Miscellany" for 7. The running
heads once said "Kernel Interfaces" and "Miscellaneous"; the catalog now says
what the home and section pages say, and every translation of section 4 is
"special files" accordingly.

### Translator notes

Where a placeholder is composed into a sentence (`{pages}`, `{link}`,
`{table}`, `{explain}`, `{when}`, `{systems}`), the English list in
`catalog/en/` carries a `// Translator note:` above the message saying what text
is inserted and its grammatical role. Read it before changing the sentence
around the placeholder: the assembled sentence must agree in case, gender and
number (the Russian `{pages}` and `{link}` messages are the cases that
broke). "Portable only" means available on all three systems (GNU/Linux,
FreeBSD, macOS), not identical behavior, and "seek" in the tar message means
moving the read position within the archive.

## Fixing a translation

Every localized page's footer has "Suggest a fix for this translation", a
prefilled new issue from `.github/ISSUE_TEMPLATE/translation_fix.yml` with the
language and the page (`translationFixHref` in `lib/i18n/fix.ts`; it also takes
the string key, which is the message's English text, for a link about one
string). The page-level link leaves the key for the reporter, who can quote the
text instead.

## Adding or changing a string

1. Write the English at the call site: `t('Your new message')`. The English
   lists in `catalog/en/` take it too (the right one of `common`, `client`,
   `man`, `server`); `tsc` rejects a message that is in no list.
2. Add its translation to all six `<lang>/` files; `tsc` lists what is missing.
3. `pnpm next:test` runs the completeness test.
4. Where a visible label sits in a control with an `aria-label`, keep the
   visible words inside the label (axe `label-content-name-mismatch`) in every
   language.
5. Changing a message's English changes its key: update every translation.

## Budgets and CSP

English pages are unchanged: no strings are added to their HTML, and no bundle
carries a catalog. The man page script for English is the script it always was
(the build erases the message wrappers); the App Router client adds the
provider, the plural picker and the `t()` wrappers
(docs/performance-budgets.md). The language switch is two server-rendered
links and renders nothing until a second language is public. A localized man
page loads its own script bundle, so no strings travel in its HTML either.
